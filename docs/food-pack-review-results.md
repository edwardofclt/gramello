## Platform and release limits

Android runtime and physical-device large-dataset performance were not checked.
Fixtures are small real SQLite packs, not evidence of million-product phone
performance. No full production dataset or nutrition release was downloaded or
published. WebKit tests use persistent disposable profiles; its default private
test contexts failed OPFS operations and are not claimed as supported here.
For WebKit's cold offline-read test all HTTP(S) requests are aborted: Playwright's
offline protocol switch failed cold file reads as well, while normal reopen and
warmed protocol-offline reads passed. This is not OS-level offline WebKit proof.
Unsupported storage retains metadata and reports the source issue.

Fallback readers load one full pack. Cross-origin integrations without CORS/CORP
may be blocked by isolation. The existing diary, recovery, navigation, barcode
and public-image fixture tests pass under the stricter headers.

## Implementation rulings

1. Gather USDA identities in bounded 500-row pages before native route writes,
   keeping index and nutrition connections separate. Cost if wrong: a few MiB of
   identity strings at the signed 100,000-food limit, not full catalog bytes.
2. Expose direct-filesystem capability and inspect staged SQLite under the reader
   lock. Cost if wrong: unsupported browsers use slower whole-pack fallback and
   installation does extra verification.
3. Enforce compiled-response isolation in a Worker wrapper plus static headers
   because the pinned framework did not propagate configured headers. Cost if
   wrong: third-party browser integrations can be affected.
4. Use `require-corp` rather than `credentialless`, and anonymous-CORS food images,
   because WebKit lacked isolation/SharedArrayBuffer with the latter. Cost if
   wrong: assets without CORS/CORP cannot render.
5. Verify cold WebKit offline access by aborting HTTP(S) traffic. Cost if wrong:
   the result does not establish OS-level offline WebKit behavior.
6. Allow an optional native fixture fetch dependency, keeping the production Expo
   default. Cost if wrong: one extra internal dependency boundary to maintain.

## Shipping gates and rollback

The follow-up branch must receive green CI and human approval before merge.
Publishing signed nutrition releases is a separate operation. Do not run that
workflow merely to ship these application fixes. Personal schema and existing
catalog/trust contracts are unchanged.

If isolating headers regress diary startup or external assets, stop rollout and
repair the headers/assets without erasing packs. Do not blindly roll browser
clients back to a pre-migration release: it cannot interpret the versioned OPFS
activation entries. A safe rollback must retain this entry decoder and async
file fallback. Installed expansion failure must leave core foods and diary data
usable. No production/staging deployment or monitoring claim is made here.
